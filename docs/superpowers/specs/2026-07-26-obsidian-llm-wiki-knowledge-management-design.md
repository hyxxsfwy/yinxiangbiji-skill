# Obsidian 精选知识库与 LLM Wiki 设计

## 1. 背景与结论

本设计用于把现有印象笔记知识组织方式简化为适合在 Obsidian 中长期手工维护、并可在后续接入 AI 半自动整理的知识体系。

印象笔记 API 的只读盘点结果如下：

- 38 个自有笔记本、2 个关联共享笔记本；
- 49,259 篇自有笔记；
- 6 个笔记本组（包含未分组笔记本）；
- 217 个标签、13 个根标签，标签最深 4 层；
- `3.归档` 包含 33,206 篇，约占全部笔记的 67%；
- `0.默认` 中微信、Twitter、微博、RSS 等自动采集内容包含 15,586 篇，约占 32%；
- 人工整理的 `1.缓存` 和 `2.专题` 合计 453 篇，不足全部笔记的 1%。

现有体系的主要问题不是标签层级太深，而是主题、领域、来源、内容类型、任务状态、个人状态和优先级同时混在标签树中。将该结构机械复制到 Obsidian 会保留复杂度，却无法形成可持续维护的知识库。

已确认采用“混合模式”：

- 历史剪藏和大规模自动采集内容继续保留在印象笔记；
- Obsidian 只迁移值得继续使用的内容；
- 原始精选资料与经过消化的知识笔记分层管理；
- 迁移由实际使用触发，不实施全量搬运；
- 当前先建立手工可维护的规则，同时为后续 LLM Wiki 半自动整理预留稳定的数据边界。

## 2. 目标

1. 让目录、Properties、标签、内部链接和书签各自只承担一种职责。
2. 把“收藏过的资料”和“已经掌握的知识”明确分开。
3. 将手工维护压缩到少量稳定字段和有限主题标签。
4. 让知识库能够通过 Bases、知识地图和双向链接形成多种视图。
5. 为 AI 自动摘要、候选双链、知识地图维护和审核队列提供机器可读结构。
6. 允许 AI 在人工制定的规则下自动审批低风险变更，只把冲突和高风险事项交给人工。
7. 所有自动修改必须可解释、可审计、可回滚。

## 3. 非目标

- 不把 49,259 篇历史笔记全量同步到 Obsidian。
- 不复刻印象笔记的全部笔记本组和笔记本目录。
- 不把 `_Apps`、任务优先级、个人状态等旧标签原样迁移。
- 本阶段不移动现有 Obsidian 文件，不改变现有导出目标。
- 本阶段不实现 LLM 模型调用、自动改写、自动移动或自动删除。
- 不用 AI 自动生成大量永久标签或无证据的语义链接。

## 4. 核心组织原则

> 文件夹决定“放在哪里”，Properties 决定“它是什么”，标签决定“涉及什么主题”，内部链接决定“与什么知识有关”，书签决定“现在常用什么”，Bases 负责动态汇总。

补充约束：

- 一篇笔记只有一个主要目录和一个主要领域；
- 跨领域关系通过内部链接和有限标签表达；
- 目录默认不超过两级业务层级；
- 历史年份不是知识分类，只允许作为精选资料的时间归档；
- 知识地图是人工选择的重要入口，不是文件清单；
- 完整列表交给 Bases 或目录索引生成。

## 6. 双层内容模型

### 6.1 精选资料

精选资料是仍值得引用、但尚未完全转化为个人知识的原文、网页剪藏、PDF 或参考内容。

满足以下条件中的至少两项才从印象笔记迁入：

- 正在被当前项目使用；
- 内容仍然有效且不容易重新找到；
- 能用一句话说明保留价值；
- 可以关联已有知识笔记或形成新知识笔记；
- 预计未来会再次引用。

不因“以后可能有用”而迁移。每周历史迁移建议限制在 5 至 10 篇。

### 6.2 知识笔记

知识笔记是经过理解、重写、总结、验证或实际使用后形成的个人知识。知识笔记不复制原文全文，而是通过内部链接引用精选资料。

示例：

```markdown
# Agent 为什么不宜加载过多 Skill

过多 Skill 会增加模型的选择干扰和上下文负担，应只加载当前任务需要的能力。

## 相关知识

- 前置知识：[[Agent 基本架构]]
- 相关方法：[[上下文工程]]
- 使用示例：[[Claude Code Skill]]

## 参考资料

- [[删掉80%的Skill，Agent反而更听话了]]
```

### 6.3 项目内容

只服务当前交付目标的材料放入 `20_项目`。项目结束后，通用知识提炼进 `10_知识库`，其余材料归档，不把整个项目目录变成永久知识分类。

## 7. Properties 规范

### 7.1 人工维护字段

日常手工管理只要求四个字段：

| 字段 | 允许值 | 说明 |
|---|---|---|
| `type` | `资料`、`知识`、`索引`、`模板` | 内容性质 |
| `domain` | `AI`、`Quant`、`软件工程`、`投资理财`、`个人成长` | 单一主要领域 |
| `status` | `待处理`、`待提炼`、`常青`、`归档` | 内容处理阶段 |
| `tags` | 最多 3 个受控主题标签 | 跨目录主题 |

精选资料模板：

```yaml
---
type: 资料
domain: AI
status: 待提炼
created: 2026-07-26
source: Evernote
source_guid:
source_url:
tags:
  - 主题/Agent
---
```

知识笔记模板：

```yaml
---
type: 知识
domain: AI
status: 常青
created: 2026-07-26
updated: 2026-07-26
tags:
  - 主题/Agent
---
```

状态转换规则：

- 新捕获内容：`待处理`；
- 确认保留但尚未消化的资料：`待提炼`；
- 已经形成稳定认识的知识笔记：`常青`；
- 不再活跃但仍需保留引用：`归档`；
- 精选资料完成提炼后转为 `归档`，新知识笔记转为 `常青`。

### 7.2 LLM Wiki 管理字段

以下字段由模板或自动化维护，不要求人工逐项填写：

```yaml
uid: note-01k2...
summary: Agent 加载过多 Skill 会增加选择干扰和上下文负担。
aliases:
  - Agent Skill 管理
review_status: ai-approved
reviewed_by: llmwiki-policy-v1
reviewed_at: 2026-07-26
llm_policy: standard
```

字段含义：

- `uid`：不随文件改名和移动变化的稳定标识；
- `summary`：一句话摘要，供搜索、Bases 和知识地图使用；
- `aliases`：同义名称和旧名称，用于候选链接消歧；
- `review_status`：`pending`、`ai-approved`、`human-approved`、`rejected`；
- `reviewed_by`、`reviewed_at`：记录审批策略和时间；
- `llm_policy`：`standard`、`strict`、`off`，`off` 禁止 AI 修改。

## 8. 标签规范

标签只表达主题，不再承担来源、领域、类型、状态或优先级。

推荐结构：

```text
主题
├─ Agent
├─ RAG
├─ OpenAI
├─ Prompt
├─ 机器学习
├─ 联邦学习
├─ Python
├─ Docker
├─ 信息安全
├─ 量化交易
├─ 股票投资
└─ PKM
```

硬规则：

1. 每篇笔记最多 3 个标签。
2. 默认只使用 `主题/<主题名>` 两层结构，极少数情况下允许第三层。
3. 预计至少 3 篇笔记会使用时，才创建永久标签。
4. 不用标签重复目录或 Properties 已表达的信息。
5. 人名、文章名、产品名和一次性概念优先使用内部链接。
6. AI 只能使用受控主题词表中的标签；新永久标签必须人工审批。

旧标签映射：

| 旧标签 | 新处理方式 |
|---|---|
| `_Apps/微信`、`Twitter`、`微博` | `source` 属性 |
| `$任务/待阅读/+++` | `status: 待提炼` |
| `$任务/待处理/***` | `status: 待处理` |
| `$状态/冷静`、`持戒`、`不爽` | 不进入知识库，必要时放入日记 |
| `$主题/$网摘` | `type: 资料` |
| `$主题/$模板` | `90_系统/模板` |
| `$主题/$资源` | `30_精选资料` |
| `$个人`、`$学习`、`$工作` | `domain` 属性 |
| `智能体Agent`、`搞懂Agent的第一步` | `主题/Agent` |
| `OpenAI开发`、`ChatGPT开发技巧` | `主题/OpenAI` |

## 9. 首页、书签、Bases 与知识地图

### 9.1 首页

`00_首页.md` 只保留当前入口、知识地图和动态视图，不罗列所有文件。

### 9.2 书签

建立三个书签组：

- `工作台`：首页、收件箱、当前项目；
- `知识地图`：AI、Quant 等领域入口；
- `动态视图`：待处理、待提炼、近期更新。

普通文章不长期加入书签。需要长期使用时，应进入知识地图或项目。

### 9.3 Bases

只建立三个核心视图：

- `全部常青知识.base`：`type = 知识` 且 `status = 常青`；
- `待处理与待提炼.base`：`status = 待处理 OR 待提炼`；
- `精选资料.base`：`type = 资料`，按领域分组、创建时间倒序。

### 9.4 知识地图

知识地图只维护核心概念、开发实践、工具平台和待研究问题等人工精选入口。完整文件列表交给 Bases。

## 10. 日常维护流程

### 10.1 捕获

所有新内容统一进入 `01_收件箱`，不在捕获时设计复杂目录和标签。

### 10.2 每周处理

每篇内容只做四选一：

1. 无持续价值：删除或继续留在印象笔记；
2. 值得保留原文：移入 `30_精选资料`，设为 `待提炼`；
3. 能形成通用认识：新建知识笔记；
4. 只服务当前任务：放入 `20_项目`。

每周只处理有限数量，不以清空历史库存为目标。

### 10.3 每月维护

- 合并同义标签；
- 删除没有继续使用价值的单次标签；
- 更新知识地图的人工精选区；
- 将完成项目归档；
- 检查收件箱和待提炼队列是否长期积压；
- 抽查一部分 AI 自动审批结果。

## 11. LLM Wiki 协作模式

### 11.1 权限分层

- 原始资料层正文只读，AI 可生成摘要、属性和链接建议；
- 知识笔记层允许 AI 补充摘要、别名、受控标签和相关知识，不得直接删除或改写人工结论；
- 知识地图划分人工精选区和 AI 自动维护区；
- `llm_policy: strict` 只允许提出建议；
- `llm_policy: off` 禁止 AI 处理。

知识地图使用明确边界：

```markdown
## 人工精选

- [[AI Agent]]
- [[RAG]]

<!-- llmwiki:auto:start -->

## AI 自动维护

- [[Agent 上下文工程]]

<!-- llmwiki:auto:end -->
```

AI 只能直接修改标记之间的内容。

### 11.2 审核架构

每项 AI 变更由四个环节组成：

1. 生成器输出结构化提案、证据、目标和置信度；
2. 独立审核模型在不依赖生成器结论的情况下复核；
3. 确定性校验器检查 Properties、路径、链接、标签词表和幂等性；
4. 审批策略根据风险等级决定自动执行或进入人工队列。

自动审批必须同时满足：

1. 操作在人工规则白名单中；
2. 存在可定位的原文或相关笔记证据；
3. 只使用已有主题词表；
4. 目标链接唯一且不存在同名歧义；
5. 生成模型与独立审核模型结论一致；
6. 格式、路径、链接和 Properties 校验通过；
7. 变更可回滚并写入日志；
8. 目标笔记没有设置 `strict` 或 `off`。

任何条件不满足时进入人工队列。

### 11.3 风险分级

| 变更 | 审批方式 |
|---|---|
| 补齐字段、规范格式 | 规则校验后自动审批 |
| 生成一句话摘要 | 有正文证据且双模型一致时自动审批 |
| 添加已有主题标签 | 命中受控词表时自动审批 |
| 添加明确且唯一的内部链接 | 双模型一致时自动审批 |
| 更新知识地图 AI 区域 | 自动审批并记录日志 |
| 生成知识笔记草稿 | 自动生成，保持 `pending` |
| 创建永久标签 | 人工审批 |
| 修改人工结论 | 人工审批 |
| 合并、移动、重命名或删除 | 人工审批 |
| 将草稿提升为常青知识 | 人工审批 |
| 修改知识地图人工精选区 | 人工审批 |

### 11.4 双向链接规则

Obsidian 的反向链接由正向内部链接自然产生。AI 每篇知识笔记默认只保留 3 至 7 个高价值关系：

- 前置或依赖；
- 同一概念的不同视角；
- 方法与实际案例；
- 明确支持、补充或冲突的观点；
- 原始资料与提炼知识。

仅出现相同关键词不足以建立链接。推荐使用带语义的列表：

```markdown
## 相关知识

- 前置知识：[[Agent 基本架构]]
- 相关方法：[[上下文工程]]
- 使用示例：[[Claude Code Skill]]
- 对比观点：[[工具越多能力越强吗]]
```

### 11.5 审核资产

未来 LLM Wiki 运行资产放在：

```text
90_系统/LLM Wiki/
├─ 审核规则.md
├─ 主题词表.md
├─ 别名词典.md
├─ 审核队列/
├─ 审核日志/
└─ 变更快照/
```

人工主要处理规则冲突、新标签、结构性变更和高风险操作。对反复出现的相同审核结果，应更新 `审核规则.md`，让后续同类项目自动审批或自动拒绝，而不是持续逐条点击。

## 12. Skill 项目变更范围

本次实现阶段只修改 Skill 项目，不移动真实知识库：

1. 在 `SKILL.md` 增加精选迁移、双层内容、Properties、主题标签和 LLM Wiki 边界规则；
2. 增加详细参考文档，保留完整的目录、审核和维护说明；
3. 增加精选资料、知识笔记和知识地图三个 Markdown 模板；
4. 扩展文档测试，验证关键字段、模板路径和安全边界；
5. 保持现有搜索导出、月度归档、图片和去重行为不变；
6. 不提交或覆盖工作区中与本设计无关的现有改动。

后续阶段可单独实施：

- 把导出目标从当前根目录迁移到 `30_精选资料/<领域>/`；
- 为导出命令增加领域、状态和受控标签参数；
- 建立主题词表、别名消歧和候选链接生成器；
- 实现生成器、独立审核器、确定性校验器和审核队列；
- 在 Git 或等效快照机制下执行可回滚的自动修改。

## 13. 异常与安全边界

- 找不到唯一链接目标时只生成候选，不自动写入；
- 摘要无法定位到原文证据时进入人工队列；
- 不允许 AI 删除原始资料或附件；
- 不允许 AI 自动创建永久标签、移动目录或提升常青状态；
- 单次自动任务限制修改数量，超过阈值必须分批；
- 同一提案重复执行不得产生重复标签、重复链接或重复地图条目；
- 自动审批结果必须记录规则版本、模型、证据和变更前后状态；
- 人工可通过 `llm_policy: off` 或保护区域立即停止 AI 修改；
- 真实知识库写入前必须验证路径位于配置的 vault 内。

## 14. 验收标准

正式规则与模板实现完成后，应满足：

1. `SKILL.md` 明确禁止全量复刻印象笔记目录和历史剪藏；
2. 明确历史资料留在印象笔记、按需迁移的判定条件；
3. 明确精选资料与知识笔记的目录和状态边界；
4. 文档列出四个核心人工字段及其允许值；
5. 文档规定标签仅表达主题、每篇最多三个、三篇复用后再建永久标签；
6. 三个模板可直接在 Obsidian 中使用；
7. LLM Wiki 规则明确原文只读、人工保护区、自动维护区和 `llm_policy`；
8. 自动审批必须经过白名单、证据、词表、消歧、双模型一致、校验、日志和可回滚检查；
9. 高风险操作始终进入人工队列；
