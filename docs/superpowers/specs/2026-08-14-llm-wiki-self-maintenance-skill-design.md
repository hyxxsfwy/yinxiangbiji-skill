# LLM Wiki 自维护技能优化设计

**日期：** 2026-08-14
**状态：** 待用户审阅
**采用方案：** Schema + 操作契约 + 确定性校验（方案 B）

## 1. 背景与目标

当前 `yinxiang-notes` 已经具备印象笔记导出、Obsidian 生命周期目录、固定受管十二领域、索引重建、链接治理、人工审批、事务回滚和完整性验收能力。现有能力重点解决“资料如何安全进入 Vault”以及“已有资料如何保持结构正确”，但还没有把 LLM Wiki 的日常维护行为收敛为可发现、可执行、可验证的技能契约。

本次参考《Karpathy 的 LLM Wiki 搭建实战：三层架构 + 三大操作，Obsidian + AGENTS.md 让知识库自我维护》，吸收其中的持久化知识、三层职责、Ingest/Query/Lint 操作闭环和工具中立 Schema 思想，不照搬文章中的 `raw/`、`wiki/` 目录，也不采用“LLM 全权写入”的宽松权限模型。

目标是在当前技能仓库中建立一套工具中立、渐进披露、默认只读、人在环审批的 LLM Wiki 自维护能力：

1. 用 Vault 根目录 `AGENTS.md` 模板表达知识库行为合约；
2. 把现有目录明确映射为 Schema、事实来源、知识维护和治理审计四类职责；
3. 把 Ingest、Query、Lint 定义为技能一级操作；
4. 用确定性 Lint 检查可由程序判断的结构问题；
5. 保持现有十二领域、生命周期目录、导出门禁和生产写入授权不变。

## 2. 非目标

本次不做以下事项：

- 不写入正式 Obsidian Vault；
- 不访问真实印象笔记账号；
- 不移动、合并、重命名或删除生产知识文件；
- 不把现有目录重构成参考文章的 `raw/` 与 `wiki/`；
- 不接入模型 API，不实现无人值守的自动摄取或自动修复；
- 不引入向量数据库、Embedding 服务或新的 Obsidian 插件依赖；
- 不自动创建永久标签，不自动把待审知识提升为常青知识；
- 不把聊天中的所有回答都归档为知识笔记。

## 3. 设计原则

### 3.1 持久化复利，而非一次性问答

Ingest 产生可追溯的待审知识，Query 只沉淀真正新增且可复用的洞察，Lint 持续发现结构漂移。每次操作都必须留下可读文件或机器可读报告，不能只在聊天中给出结论。

### 3.2 人负责方向，LLM 负责记账

用户负责选择资料、提出问题和批准高风险变更。LLM 负责摘要、证据定位、交叉引用、索引建议和审计报告。人工结论、常青状态、永久分类以及文件生命周期操作仍由人决定。

### 3.3 权限由内容性质决定

`30_精选资料` 是事实来源层，正文只读；`20_知识笔记` 是受控知识层，允许创建待审草稿和修改明确的自动维护区；`80_系统/知识库治理` 保存规则、队列、报告和日志。路径不等同于授权，`llm_policy`、保护区标记和用户本次授权共同决定是否可写。

### 3.4 默认只读，写入必须显式升级

本次提供的 Lint 命令只读 Vault 并输出报告。即使问题可确定性修复，也只标记 `fixable: true`，不提供自动写回参数。后续若实现安全修复，必须另行设计确认词、事务前像和回滚验收。

### 3.5 先使用现有索引和链接

当前规模优先使用目录索引、知识地图、Markdown 全文搜索和 Wikilink。不因参考文章提到检索扩展而提前引入向量基础设施。

## 4. 架构映射

参考文档的三层架构映射到现有体系如下：

| 职责 | 当前落点 | 写入策略 |
| --- | --- | --- |
| Schema 行为配置 | Vault 根目录 `AGENTS.md`；仓库模板 `templates/obsidian-agents.md` | 模板随技能维护；部署到生产 Vault 另行授权 |
| Raw sources 事实来源 | `30_精选资料/<领域>/YYYY年MM月/` | 原始正文只读，只允许受控属性与链接建议 |
| Wiki 知识维护 | `20_知识笔记/<领域>/`、`目录索引.md`、`知识地图.md` | 新内容默认待审；人工区不可改写 |
| Governance 治理审计 | `80_系统/知识库治理/` | 保存规则、审核队列、审核日志和报告 |

`10_项目`、`01_收件箱`、`90_归档` 和 `99_废纸篓` 继续承担现有生命周期职责，不纳入 LLM 自动维护写集。

## 6. AGENTS.md Schema 设计

`templates/obsidian-agents.md` 是部署到 Vault 根目录的工具中立模板，必须包含以下内容：

1. 知识库目标和人机分工；
2. 当前生命周期目录与四类职责映射；
3. 受管十二领域和唯一主领域约束；
4. Ingest、Query、Lint 的入口和完成条件；
5. Properties、状态、来源和链接规则；
6. 自动区、人工保护区与 `llm_policy` 权限矩阵；
7. 操作日志和审核队列格式；
8. 禁止删除、移动、合并、重命名、创建永久标签和提升常青状态；
9. 发现歧义、冲突或证据不足时停止写入并提交人工审核；
10. 任何生产写入前确认目标位于配置的 Vault 内并获得用户授权。

模板不得包含设备专属绝对路径、账号信息、Developer Token、NoteStore URL 或当前日期。它描述稳定合约，不复制仓库 README 的安装说明。

## 7. 三大操作契约

### 7.1 Ingest：逐篇摄取

**触发语义：** “处理这篇资料”“摄取这篇文章”“从这份精选资料提炼知识”。

**输入：** 一篇位于 `30_精选资料` 的明确 Markdown 文件。默认一次只处理一篇；批量任务必须先生成逐篇清单并由用户确认范围。

**读取顺序：**

1. 读取 Vault 根目录 `AGENTS.md`；
2. 读取目标资料的完整正文和 frontmatter；
3. 读取对应领域目录索引与知识地图；
4. 搜索已有同题知识、实体、概念和对比内容；
5. 沿现有高价值链接读取必要上下文。

**建页门槛：**

- 原始资料本身继续作为来源，不复制第二份“来源摘要页”；
- 具体实体或工具只有在资料中存在专门论述且能形成独立结论时才建知识页；
- 抽象概念至少获得两个独立来源支持；首次出现只进入待审候选；
- 对比笔记必须有两个以上来源，且存在差异、冲突、取舍或互补关系；
- 证据不足、主领域不唯一或同名目标有歧义时只生成审核项。

**允许产物：**

- `20_知识笔记/<领域>/` 下的待审知识草稿；
- 对已有 `llm_policy: standard` 知识笔记自动区的证据化补充；
- 目录索引重建建议；
- 知识地图自动区更新建议；
- 审核队列记录和操作日志记录。

**完成条件：** 每项新结论能追溯到来源；新链接目标唯一；草稿状态为 `待提炼`、审核状态为 `pending`；变更清单明确；未修改原始正文和人工保护区。

### 7.2 Query：查询并选择性沉淀

**触发语义：** “基于知识库回答”“比较这些观点”“把有价值的结论沉淀下来”。

**读取顺序：**

1. 读取 `AGENTS.md`；
2. 读取 `20_知识笔记/目录索引.md` 和相关领域索引；
3. 读取知识地图中的相关入口；
4. 沿 Wikilink 阅读知识笔记；
5. 必要时回到 `30_精选资料` 核对原始证据。

**回答契约：** 区分已知事实、来源观点、跨来源推断和未知项；引用具体知识页或来源页；存在冲突时并列呈现，不擅自消解。

**沉淀门槛：** 只有同时满足以下条件才建议归档：

- 回答形成了现有页面中没有的综合结论、对比框架或稳定连接；
- 结论至少有两个可定位来源，或一个来源加明确的实践证据；
- 未来可能再次使用；
- 能确定唯一领域和清晰标题；
- 不只是对现有页面的改写、摘抄或聊天式表达。

归档内容使用知识笔记或对比笔记模板，默认 `status: 待提炼`、`review_status: pending`。未达到门槛时只回答，不写文件。

### 7.3 Lint：只读健康检查

**触发语义：** “检查 Wiki”“运行 Lint”“审计知识库健康状态”。

**命令接口：**

```powershell
python scripts/lint_llm_wiki.py --vault "<Vault 路径>"
python scripts/lint_llm_wiki.py --vault "<Vault 路径>" --format json
```

未显式传入 `--vault` 时，可通过现有运行时配置读取 `OBSIDIAN_VAULT_PATH`；无论来源如何，路径都必须通过 Vault 根目录和边界校验。

**确定性检查：**

- 必需目录与 `AGENTS.md` 是否存在；
- `20_知识笔记` 和 `30_精选资料` 的 Markdown 是否具有合法 frontmatter；
- `type`、`domain`、`status`、`review_status`、`llm_policy` 是否属于允许值；
- 知识笔记是否具有可定位来源；
- Wikilink 是否存在唯一目标；
- 知识笔记是否没有任何入链；
- 知识地图自动区标记是否成对且顺序正确；
- 目录索引是否遗漏或错误收录受管内容；
- 对比笔记是否至少引用两个来源；
- 操作日志格式是否可解析且保持时间顺序。

**判断性检查：** 矛盾观点、过时结论、是否值得合并、是否应提升常青、是否应创建永久主题，只能作为 `manual_review` 报告项，不能由脚本判定正确答案。

**报告格式：**

```json
{
  "ok": false,
  "vault": "<规范化路径>",
  "checked_at": "<ISO 8601>",
  "summary": {
    "error": 1,
    "warning": 2,
    "manual_review": 1
  },
  "issues": [
    {
      "code": "BROKEN_WIKILINK",
      "severity": "error",
      "path": "20_知识笔记/AI/示例.md",
      "detail": "目标不存在或不唯一",
      "fixable": false
    }
  ]
}
```

文本输出面向人工阅读，JSON 输出用于测试和后续自动化。错误存在时进程返回非零；仅有 warning 或 manual_review 时报告非空但可使用单独退出码区分。脚本不修改 Vault，也不写报告文件，除非未来获得独立设计和授权。

## 8. 页面和元数据契约

### 8.1 精选资料

继续使用 `type: 资料`、唯一 `domain`、`status: 待提炼`、`review_status: pending` 和 `llm_policy: strict`。原始正文只读；允许在不改写正文的前提下提出摘要、链接和分类审核建议。

### 8.2 知识笔记

知识模板保留当前字段，并明确增加或收紧：

- `sources`：一个或多个来源 Wikilink；
- `summary`：一句可验证摘要；
- `status: 待提炼`；
- `review_status: pending`；
- `llm_policy: standard | strict | off`。

正文固定包含核心结论、依据与推导、相关知识和参考资料。没有来源的知识草稿只能进入人工审核，不得通过 Lint。

### 8.3 对比笔记

对比笔记仍属于 `type: 知识`，不扩展全局 `type` 词表；使用 `knowledge_kind: 对比` 区分。它必须至少引用两个来源，并明确共同点、差异、冲突、适用条件和待验证项。

### 8.4 索引、知识地图和操作日志

- 目录索引是确定性完整视图，可重建，不保存人工评语；
- 知识地图是选择性入口，人工区受保护，AI 只维护标记区；
- 操作日志位于治理区，采用只追加格式，至少记录时间、操作类型、输入、读取范围、建议写集、实际写集、审核状态和问题数量；
- 本次只定义日志契约和模板，不向生产 Vault 写入日志。

## 9. Lint 实现边界

`scripts/lint_llm_wiki.py` 优先复用现有实现：

- 使用 `scripts.runtime` 读取本地配置；
- 使用 `scripts.vault_state.require_path_within_vault` 做路径边界校验；
- 复用 `scripts.domain_taxonomy` 的固定受管领域注册表；
- 复用或提取 `scripts.restructure_obsidian_vault` 中的 frontmatter、Markdown 引用和本地链接扫描能力；
- 不复制一套不同语义的 Wikilink 解析器。

如果直接导入重组脚本导致循环依赖或 CLI 副作用，则只把稳定的纯函数提取到小型共享模块，并保持现有重组测试通过；不借本次任务重构无关代码。

## 10. 错误处理与退出码

Lint 使用稳定问题代码，便于测试和后续消费。最低覆盖：

- `MISSING_SCHEMA`
- `MISSING_REQUIRED_DIRECTORY`
- `INVALID_FRONTMATTER`
- `INVALID_PROPERTY_VALUE`
- `MISSING_SOURCE`
- `BROKEN_WIKILINK`
- `AMBIGUOUS_WIKILINK`
- `ORPHAN_KNOWLEDGE_NOTE`
- `INDEX_DRIFT`
- `INVALID_AUTO_REGION`
- `INSUFFICIENT_COMPARISON_SOURCES`
- `INVALID_LOG_ENTRY`

建议退出码：

- `0`：无 error；允许存在 warning 或 manual_review；
- `1`：发现一个或多个 error；
- `2`：参数、配置、Vault 路径或报告生成失败。

任何单文件解析失败都应形成问题项并继续扫描其他文件；无法确认 Vault 边界时必须立即失败。

## 11. 测试策略

### 11.1 技能 RED 基线

使用不包含新增规则的当前技能，分别执行 Ingest、Query、Lint 模拟任务，记录以下失败信号：

- 未读取 Schema 或索引就开始处理；
- 把原始资料改写为知识页；
- 没有建页门槛，产生单来源抽象概念；
- Query 的普通回答也被无条件归档；
- Lint 混淆可确定问题和需人工判断的问题；
- 未给出变更清单、来源证据或审核状态。

只有基线确实出现的问题才写入技能约束，避免为假设性失败堆砌规则。

### 11.2 文档契约测试

在 `tests/test_skill_documentation.py` 中先增加失败断言，再实现资产：

- 新增文件存在且由 `SKILL.md` 直接路由；
- AGENTS 模板包含三层映射、三大操作和权限矩阵；
- 模板使用现有生命周期目录，不出现要求迁移到 `raw/` 或 `wiki/` 的指令；
- 知识和对比模板包含来源与待审状态；
- 文档明确 Lint 默认只读、生产 Vault 写入另行授权。

### 11.3 Lint 单元与集成测试

所有测试只使用临时 Vault：

- 合法最小 Vault 返回 `ok: true`；
- 缺 Schema、非法字段、缺来源、断链、歧义链接、孤儿页、索引漂移、损坏自动区和单来源对比分别产生稳定问题代码；
- 代码块中的伪链接、HTTP 链接、URL 编码路径和带显示文本 Wikilink不误报；
- 输入路径逃逸 Vault 时立即失败；
- 运行前后文件哈希不变，证明 Lint 只读；
- JSON 可稳定解析，文本输出不泄露配置秘密。

### 11.4 前向验证

完成实现后，使用与基线相同的三个场景加载新技能，验证：

- Ingest 先读 Schema，遵守逐篇和建页门槛；
- Query 能判断“只回答”与“建议沉淀”；
- Lint 能区分确定性错误和人工判断项；
- 所有建议写入均保持待审，不越过人工保护区。

## 12. 验收标准

只有同时满足以下条件，才可声明方案 B 完成：

1. `SKILL.md` 可发现 Ingest、Query、Lint，并直接链接操作 reference；
2. `templates/obsidian-agents.md` 完整表达 Schema，且不含设备专属信息；
3. 三项操作均具有输入、读取顺序、允许写集、禁止项、人工审批点和完成条件；
4. 现有十二领域与生命周期目录测试保持通过；
5. Lint 在临时 Vault 上覆盖约定问题代码，且前后哈希一致；
6. 技能前向测试相较基线消除已观察到的关键失败；
7. `python -m unittest` 全量通过；
8. 技能格式验证通过；
9. `git diff --check` 通过；
10. 正式 Vault 和真实印象笔记账号在整个实施过程中保持未写入、未访问。

## 13. 实施顺序

设计批准后再编写实施计划，建议按以下顺序拆分：

1. 运行三个技能基线场景并保存证据；
2. 增加文档和模板的失败契约测试；
3. 编写操作 reference 与 AGENTS、对比模板；
4. 更新 `SKILL.md` 和现有知识管理 reference；
5. 增加 Lint 失败测试；
6. 实现只读 Lint；
7. 运行全量测试和技能前向验证；
8. 自审差异、检查生产边界并提交。

## 14. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 照搬参考目录破坏现有结构 | 明确职责映射，测试禁止强制 `raw/`、`wiki/` 迁移 |
| AGENTS 与 SKILL 规则漂移 | 共享稳定术语，并用文档契约测试检查关键门禁 |
| Lint 误把判断问题当错误 | 只编码可确定规则，其余归入 `manual_review` |
| 链接解析重复并产生不同语义 | 复用或提取现有扫描纯函数 |
| 技能内容过长、触发后占用上下文 | `SKILL.md` 只路由，详细操作放一级 reference |
| 自动维护越权修改生产 Vault | 本轮脚本只读，无修复参数；生产部署另行授权 |
| 单来源内容被过度抽象 | 概念和对比设置多来源门槛，待审状态不等于常青知识 |
